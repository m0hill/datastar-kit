Audit Summary

Datastar Kit SDK

Scope: SDK package, website, docs, official ports, and runnable examples. Datastar Pro examples stayed out of scope.

d46f524

Plugin Attribute Interface

Strong
  • Files: SDK `ds` attributes, custom plugin/action examples, website docs, SDK tests.
  • Problem: App plugin attributes required raw `data-*` props and manual expression serialization.
  • Solution: Add `ds.pluginAttr(name, value?)` with normal Datastar expression serialization.
  • Leverage: Callers get one small Interface for app-defined attribute plugins.
  • Locality: Plugin name validation and value serialization live in one Module. 
flowchart LR
  A["Before: callers know raw data-alert"] --> B["manual value expression"]
  C["After: ds.pluginAttr"] --> D["data-alert + serialized value"]
  D --> E["Datastar plugin"]

6c1db10

Browser Scripts Became Modules

Strong
  • Files: Custom Event, Sortable, Web Component TSX and public JavaScript modules.
  • Problem: Browser-only DOM code lived in inline `unsafeHtml(...)` strings.
  • Solution: Move DOM behavior into served module scripts and keep TSX on markup.
  • Leverage: Example authors get normal JavaScript editing and module loading.
  • Locality: Browser behavior changes stay in browser-owned files.

0e58afa

Signal Refs In Expressions

Strong
  • Files: Official example TSX files.
  • Problem: Raw `$signal` names and action calls were duplicated inside expression strings.
  • Solution: Use `ds.signal`, `ds.local`, `ds.state(...).$`, and tagged `ds.expr` interpolation.
  • Leverage: Renames and action serialization go through typed refs.
  • Locality: Signal names concentrate at definitions instead of string interiors.

Before

`ds.expr("$count++")`

to

After

`ds.expr`${"$"}{count}++``

6df4b18

Normal Datastar Boundary

Strong
  • Files: SDK plugin attributes, docs, tests, official examples metadata.
  • Problem: Keyed plugin attributes were added only because Match Media exists in Datastar Pro.
  • Solution: Remove Pro-driven keyed support and keep Counter/Counters naming for the JSX port.
  • Leverage: Normal Datastar users get the helper they need.
  • Locality: Pro catalog concerns stay out of the normal SDK Interface.
flowchart TB
  A["Datastar Kit"] --> B["Normal Datastar"]
  A -. rejected .-> C["Datastar Pro examples"]
  B --> D["pluginAttr('alert')"]
  C -. not shaping Interface .-> E["match-media / rocket"]

2a7e304

Counter Response Defaults

Strong
  • Files: `examples/hono-official-examples/src/examples/counters.tsx`.
  • Problem: The counter mixed raw `204` and `reply.directHtml(...)` into a normal Datastar response path.
  • Solution: Use `reply.done()` and `reply.patch(...)`; preserve the user counter cookie.
  • Leverage: The example teaches default SDK responses.
  • Locality: Direct responses remain reserved for direct-response cases.

b6f3247

Durable Object Row Interface

Strong
  • Files: `examples/worker-do-hono-live-todos/src/realtime/hub.ts`.
  • Problem: SQL rows intersected with the public `Todo` Interface and blurred number/boolean fields.
  • Solution: Add explicit `TodoRow` and map it to `Todo` at the storage boundary.
  • Leverage: Callers receive clean application todo data.
  • Locality: SQL coercion lives at the Durable Object read Seam.
flowchart LR
  DB["SQLite row\ncompleted: 0 | 1"] --> R["TodoRow"]
  R --> M["map at DO boundary"]
  M --> T["Todo\ncompleted: boolean"]

533622b

HTML Name Validation

Strong
  • Files: HTML renderer, root exports, SDK tests, website docs.
  • Problem: Text and values were escaped, but tag and attribute names crossed the renderer boundary verbatim.
  • Solution: Add `HtmlNameError` and validate names before serialization.
  • Leverage: The same renderer Interface owns a deeper safety boundary.
  • Locality: Name safety is one HTML Module concern.

3b8a741 + 732a35b

Regex Expression Escaping

Strong
  • Files: Expression Module, `ds` exports, SDK tests, API docs.
  • Problem: `ds.regex("a/b")` rendered an invalid slash-delimited JavaScript regex.
  • Solution: Validate with `RegExp(...)` and render `new RegExp(pattern, flags)`.
  • Leverage: Callers pass ordinary constructor inputs.
  • Locality: Regex escaping and errors stay in the expression Module.
sequenceDiagram
  participant Caller
  participant Regex as ds.regex
  participant Expr as Datastar expression
  Caller->>Regex: pattern "a/b", flags "i"
  Regex->>Regex: RegExp(pattern, flags)
  Regex->>Expr: new RegExp("a/b", "i")

d1fa9c9

Worker Live Todo Locality

Strong
  • Files: D1 Worker todos and Durable Object todos examples.
  • Problem: Room lookup was repeated and single patch responses were wrapped in streams.
  • Solution: Centralize room lookup locally and use `reply.patch(...)` for single patches.
  • Leverage: Readers see room boundary and response intent.
  • Locality: Room naming and patch semantics concentrate in one place.

Before

getByName("todos") x 4

stream([event.patch(...)])

to

After

liveRoom(env)

reply.patch(...)

98ae64c

Package Changelog Locality

Worth exploring
  • Files: `packages/datastar-kit/CHANGELOG.md`.
  • Problem: Public SDK changes existed in docs and audit notes but not the package changelog.
  • Solution: Add an Unreleased section for changed Interfaces.
  • Leverage: Release readers get the API delta in one place.
  • Locality: Release notes live with the package.

Top Changes

  • `ds.pluginAttr(...)`: highest leverage. It turns a real Datastar extension seam into a small SDK Interface without inventing a new layer.
  • Signal refs in examples: highest locality. Signal and action mistakes now concentrate at definitions instead of raw expression strings.
  • HTML name validation: strongest safety improvement. The renderer now owns the complete serialization boundary for normal output.
  • Datastar Pro boundary: important scope control. Normal Datastar stays clean, and Pro examples do not shape this SDK.
  • Durable Object row typing: best example correctness fix. SQL transport shape no longer leaks into the public todo Interface.
